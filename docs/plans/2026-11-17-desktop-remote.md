# 桌面应用连远端的 DSH Web

- 日期：2026-11-17
- 相关：维护者 2026-11-17 在会话里提出（应用里不要写死地址，能直接填远端地址）
- 一起改：[桌面应用](2026-10-16-desktop-app.md)（壳、窗口、引擎）、[手机 App](2026-10-24-mobile-app.md)（手机遥控电脑是另一条路）

## 为什么

- 团队可以跑在别的机器上（NAS、服务器、Docker）。手机、平板和没装 DS Bot 的电脑只想看那台机器上的团队。今天只有一条路：在浏览器里打开 `dsh web` 打印的地址。没有托盘，没有单实例，关掉标签页就没了。
- 桌面应用本来就是「加载引擎自己的网页前端」的壳（[桌面应用](2026-10-16-desktop-app.md)）。窗口里是 DSH Web 的页面，壳负责窗口、托盘、退出。把壳接到远端的页面上，是改动最小的一条路：插件、团队、会话都还在那台机器上，应用只是换了一个加载地址。
- 地址不能写死：端口、域名、一次性 token 每台机器、每次 `dsh web` 都不一样。所以地址由用户填，存在应用自己的 `userData` 里，下次启动照旧用。

## 已定的行为

### 1. 地址从哪来

- 优先级：`DS_BOT_REMOTE` 环境变量 > `userData/remote.json` 的 `url` > 本机 Host。
- 空白按「没有」处理：环境变量是空白、文件里的 `url` 不是字符串、或者没有地址时，应用起自己的 Host，和今天一样。
- 只接受 http/https。别的写法停在失败页（或地址窗口里的红字），**不退回本机 Host**：那会让人以为连着远端，其实看的是本机。
- 地址分三份：
  - `url`：带 `?token=…` 的启动地址，第一次加载用，页面用它换该 Host 的 cookie。
  - `root`：去掉 query 和 `#` 的地址，之后的每个窗口用它，靠 cookie 进。挂在路径下的部署（`https://host/team/`）保留路径。
  - `origin`：`协议//主机[:端口]`，页面所属的来源，窗口的 `--ds-bot-origin`、IPC 的 `assertWindow`、`will-navigate` 都用它。

### 2. 怎么填

- 托盘菜单里〔打开〕下面多一项「远程 DSH Web…」，各语言的文案在 `SHELL_TEXT`。
- 点开是应用自己的一个小窗口（520 × 250，`data:` 页加 `remote-preload.cjs`，不是系统对话框）：一个地址字段，〔连接〕〔改用本机〕〔取消〕。字段预填当前地址的 `root`，光标在字段里，Enter 连接，Esc 取消。
- 〔连接〕由主进程校验（`remoteOf`）：不是地址、不是 http(s) 时窗口不关，字段下面一行红字说清哪里不对，草稿留着。
- 校验通过后写 `userData/remote.json`，然后 `app.relaunch()` 加 `app.quit()`。走已有退出流程：本机 Host 先停，正在复制的数据先停到安全点。
- **为什么重启而不是热切**：模式决定整条启动路径（选不选位置、起不起 Host、窗口属于哪个来源、`assertWindow` 认哪个地址），热切会同时留着两个模式的东西，而且本机 Host 和远端页面共用窗口的 session。重启一次只花几秒。
- 〔改用本机〕发空地址：删掉 `remote.json`（不留空文件），同样重启。
- 地址没变（含 token 完全相同）时什么都不做，不重启：字段里再按一次〔连接〕不该重启应用。

### 3. 启动过程

- 启动窗口照旧先出来，阶段还是「数据」和「引擎」，但两步都不做事：不选位置、不建数据文件夹、不起 Host。启动窗口按「以后的启动」显示：没有首次启动的选择框，没有磁盘提示，〔换个位置…〕不响应。
- 团队窗口显示前加载远端页面：第一次用带 token 的 `url`，之后（窗口被关掉重建、重试）用 `root`。`remoteCame` 只在第一次加载成功后置位，所以 token 失败一次还能再用。
- 页面没回答（连不上、401、证书错误）时进失败页，说清是哪个地址没回答，并提示启动地址只能用一次、要从那台机器的 `dsh web` 重新取。
- 加载完成之后按老规矩走：页面报 `ds-bot:ready`，启动窗口量好矩形再交接。远端跑同一套插件时行为一致；远端没装插件时，20 秒后启动窗口进失败页（团队视图没报 ready），日志里有记录。

### 4. 远端模式下本机不动的东西

- 不起 Host 进程，不分配端口，不写 `DSH_HOME`，不读也不写 `~/.dsh`。
- 不选数据位置：`locations.json` 既不读也不写，`start-frame.json` 和 `remote.json` 照旧在应用的 `userData` 里。
- 设置里的「数据位置」显示远端 `origin`，没有〔更改…〕；`ds-bot:move-data` 直接答 `false`。
- 应用不检查更新（更新挂在起 Host 的那条路上）。
- 托盘、单实例、关窗隐藏、日志都在本机照旧。

### 5. 安全

- 地址里的 token 就是那台机器上的登录凭据，而那台机器上的 Bot 能执行 shell 命令。所以 token 泄漏等于那台机器上的远程代码执行。应用只在 `userData/remote.json` 里存它，和 `locations.json` 同一层。
- 失败页、日志、控制台只出现 `root`，不出现 token。
- 直连域名时 DSH 的登录只接受回环来源：要让域名直连，Host 侧得把域名放进 `DSH_TRUSTED_HOST`（见 `docker-compose.yml`）。否则用 `ssh -L 3080:127.0.0.1:3080 用户@那台机器` 或本机反向代理，把地址落在 `127.0.0.1` 上，再用 `dsh web` 打印的地址。

## 不做什么

- 不做账号、配对、端到端加密：那是 [手机 App](2026-10-24-mobile-app.md) 那条路（电脑只往外连、手机配对）。这里只复用 DSH Web 自己的 token 和 cookie。
- 不改 DSH 的登录和来源规则。
- 不在同一个实例里同时显示本机和远端。

## 已知限制

- Bot 浏览器面板和电脑使用是本机的壳做的（`bot-browser.mjs` 的 webview、`computer-cursor.mjs` 和 `computer-indicator.mjs` 的指示条）：远端团队点开这些会试图在本机开页面、看本机的屏幕，和远端 Host 上的 Bot 对不上。远端模式下这两块没有验证过，先按不可用对待。
- 应用注入的字体和卡片样式（`fonts.css`、`page-card.css`）只在远端页面的 CSP 允许时生效；样式和主题（`start-frame.json`）是壳的偏好，远端页面不一定跟随。
- 〔改用本机〕在 `DS_BOT_REMOTE` 还有值时不起作用（环境变量优先）。这是有意的：环境变量是测试和临时运行的开关。
- 远端必须是带了 ds-bot 插件的 DSH Web，否则看到的只是 DSH 自己的页面。
